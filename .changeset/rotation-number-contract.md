Rotation numbers are carried through the contract and the tracking spec, never interpreted (calchas design brief D2, 2026-10-08: a fill's `YG 913 …` rotation was parsed and then lost before it could place the bet on a doubleheader game).

- **`ContractLegSpec.RotationNumber` (new).** `mapParseResultToContractLegSpec` sets it from the parse for a straight, and for each parlay or round-robin leg from that leg's own number (`YGP 872 Cardinals/Cubs o8.5 @ -110 & 701 Lakers @ +120 & Yankees @ -150 = $100` maps to 872, 701 and unset). It is unset when the message has no rotation.
- **`contract.RotationNumber` is now actually set.** The stamp was guarded by `'RotationNumber' in contract`, which is always false for a freshly built contract, so the documented field was never populated; the library's own test only checked it under the same guard. Every non-writein contract parsed with a rotation now carries it, and the test asserts it unconditionally (and asserts its absence when there is no rotation).
- **A rotation with no team throws.** `YG 913 ml +100 = 1` booked a moneyline on a team named "ml". A bare `ML` marker is not a moneyline contestant (`isMoneylineContestant("ml")` is false), so this, `YG 913 F5 ml …`, `YG 913 G1 ml …` and the rotation-less `YG ml +100 = 1` throw InvalidContractTypeError. `YG 913 Rays ml +100 = 1` is unchanged.
- **BREAKING: rotation numbers no longer imply a sport (removed, not optioned).** `inferSportAndLeague` mapped rotation ranges to a sport (100-499 Football, 500-799 Basketball, 800-899 and 9900-9999 Baseball). Books renumber by season and reuse numbers, the ranges had gaps (MLB's 9xx fell through), and when it did fire it returned early and could override an explicit sport. Its one current consumer (calchas) lets the parser's sport outrank its per-chat default, so a wrong inference beat a correct default. It was removed rather than put behind an option because no consumer wants it on: an off-by-default option nobody enables is dead code, and catalogue knowledge (rotation ranges, +1000 derivative offsets, 99xx and 7-digit numbers) belongs to the consumer that owns the catalogue. `contract.Sport` now comes only from an explicit league or sport in the message (`league:NFL`, `NFL Dolphins …`) or from sport-specific grammar (e.g. innings). `inferSportAndLeague(explicitLeague?, explicitSport?)` drops its first `rotationNumber` parameter; direct callers must drop that argument.
